# Local ↔ dot Handoff

本地项目执行，dot 独立审核，结果由本地直接取回。

一套适用于多项目、长文档与跨会话协作的开源交接方法，附可复用 Skill、回执模板和 UTF-8 分片校验工具。它解决的是“材料到底有没有收全、审的是哪个版本、谁有权采用”的问题，不是新的通信服务。

## 为什么做这个

在多项目长文本审核实践中，发送成功很容易被误记成全文核收；旧审核可能被当成新版结论；双方反复粘贴规则和整稿又会占满上下文。另一次实际使用中，本地向审核会话提交及主动读取审核结果可用，审核端反向发回却失败。

因此将协作收敛到固定入口、完整材料、可核验回执和本地主动取回。上述单向可用只是当时观察到的兼容/路由现象，根因未确认，不代表平台永久只支持单向通信。本项目不承诺修复平台接口，也不要求所有用户放弃可正常工作的双向通道。

在随后一次闭环中，多个独立执行项目自行打开同一个共享规则页，分别确认自己的入口、暂停范围与定时任务处理结果；其中一个项目还主动取回指定版本的审核回执并确认文件身份。规则只维护一份，作者不必搬运全文。这是已观察到的案例，不等于所有项目或所有客户端都已接通。

## 工作模式

1. 确定项目执行入口、审核入口、当前版本、允许修改范围与冻结范围。
2. 本地提交完整文件及简短清单；完整附件可用时优先附件，只有文本通道时才无损分片。
3. 审核端实际读回并核对字节与版本，先给材料核收结果，再做独立内容审核。
4. 本地主动读取完整审核结果，逐项修改、连读，再提交新版。
5. 按项目所有者的批准规则采用正式版本；局部通过不自动解除其他暂停范围。

始终分开：**发送成功 → 完整核收 → 内容审核 → 授权采用**。哈希一致不证明认真读过，更不证明文学质量合格。

## 省上下文

将稳定规则保存在用户授权的共享说明页（例如 ChatGPT Page），后续只发版本、变更范围、完整材料入口和待决问题。先确认接收端确实有权限读取该页。不要用目录或摘要替代需要审核的完整正文；已经核收的同版文件可引用，不必重复贴满会话。

## 文件结构

- `skills/local-dot-handoff/SKILL.md`：通用交接 Skill。
- `skills/local-dot-handoff/references/`：分片契约与三种回执模板。
- `skills/local-dot-handoff/scripts/handoff_text.py`：不联网的 UTF-8 分片、重组、长度与 SHA-256 校验。
- `examples/`：完全虚构的演示文件和状态记录。
- `docs/adoption.md`：如何在既有项目技能中接入。
- `tests/`：传输完整性测试。

## 使用

将 `skills/local-dot-handoff` 按目标客户端支持的个人技能安装流程安装。安装本仓库不会自动获得通信权限、访问本地文件或创建定时任务。客户端能力与入口以实际工具为准。

```sh
python3 skills/local-dot-handoff/scripts/handoff_text.py split examples/sample.md /tmp/handoff-demo-parts --handoff demo-r1 --chunk-size 8
python3 skills/local-dot-handoff/scripts/handoff_text.py join /tmp/handoff-demo-restored.md /tmp/handoff-demo-parts/*.json
python3 -m unittest discover -s tests -v
```

输出目录应无同名分片，重组目标应不存在；工具拒绝覆盖。字符数按 Unicode code point 计算，不等于汉字数或 JavaScript 字符串长度。CRLF、BOM、emoji、组合字符、HTML 实体和尾空格原样保留。JSON 只解码一次。

## 边界

- 文学、工程或研究的质量判断仍使用各自专业方法；此工具只验证传输身份。
- 每日阅读数量、工作时间、项目存储规则属于用户自己的约定，不是本仓库的默认要求。
- 不能因为一个项目通信成功，就宣称全部项目已接通。
- 不自动发布稿件、不自动批准版本、不覆盖冻结章节、不新建替代项目。
- 公开仓库仅含脱敏方法与虚构示例，不含实际稿件、真实会话标识、私人链接或凭证。
